# `init.sh` Design

The gate is the loop's only objective signal. If it is slow it gets skipped; if it is noisy it gets ignored; if it demands green on a codebase that is not green it never runs at all. Design for all three.

## Contract

```bash
./init.sh baseline        # capture current failures → baseline.json
./init.sh fast [scope]    # affected module/package only — per-feature
./init.sh full            # everything — before handoff
```

Exit `0` when there are **no new failures relative to baseline**. Exit non-zero when there are, and print exactly which tests are new failures.

Output must distinguish three sets: still-failing (in baseline, ignore), newly-failing (regressions, stop), and newly-passing (a baseline failure got fixed — good news, but prompt to re-baseline deliberately rather than silently).

## Why baseline-diff, not pass/fail

A pass/fail gate on an enterprise Java repo usually fails on the first run for reasons that have nothing to do with the current work — a flaky integration test, a test that needs a database nobody has running locally, something broken on main last Tuesday. A gate that is red before you start is a gate you disable.

Baseline-diff answers the only question the loop actually needs: *did I break something that was working?*

## Why two lanes

The fast lane runs on both sides of every feature. At a fifteen-minute suite, a single-lane gate adds thirty minutes of overhead per feature and the loop stops being usable. Scope the fast lane to the module or package the feature touches — `gate_scope` in the feature frontmatter carries this — and reserve the full run for the end.

The tradeoff is real: a fast lane can miss a break in an untouched module. That is what the full lane is for, and it is why the loop never opens a PR.

## Determinism

- Fixed random seeds; no `Random` without one.
- No dependence on wall-clock time — inject a `Clock`.
- No network calls in the fast lane. Integration tests requiring containers belong in the full lane, gated on availability.
- Do not depend on test execution order.
- Pin the JVM and build-tool version through the wrapper.

If a test is irreducibly flaky, put it in the baseline and note it. An honest exclusion beats a gate nobody trusts.

## Maven template

```bash
#!/usr/bin/env bash
# Generated by harness init. Review before first run.
set -uo pipefail
cd "$(dirname "$0")/.." || exit 1

MODE="${1:-fast}"
SCOPE="${2:-}"
BASELINE=".harness/baseline.json"
MVN="./mvnw"; [ -x "$MVN" ] || MVN="mvn"

run_tests() {
  if [ "$MODE" = "fast" ] && [ -n "$SCOPE" ]; then
    "$MVN" -q -B test -Dtest="*${SCOPE}*" -DfailIfNoTests=false 2>&1
  elif [ "$MODE" = "fast" ]; then
    "$MVN" -q -B test 2>&1
  else
    "$MVN" -B verify 2>&1
  fi
}

# Surefire XML is the reliable source; console output format varies by version.
collect_failures() {
  find . -path '*/target/surefire-reports/*.xml' -newermt '-1 hour' 2>/dev/null \
    | xargs grep -l '<\(failure\|error\)' 2>/dev/null \
    | while read -r f; do
        cls=$(grep -o 'classname="[^"]*"' "$f" | head -1 | cut -d'"' -f2)
        grep -o 'name="[^"]*"' "$f" | cut -d'"' -f2 | while read -r m; do
          echo "${cls}#${m}"
        done
      done | sort -u
}

# Count executed tests. A scope filter that matches nothing exits 0 and reports
# no failures — a green gate that tested nothing. This is the failure mode most
# likely to let a regression through, so assert on it explicitly.
count_executed() {
  find . -path '*/target/surefire-reports/*.xml' -newermt '-1 hour' 2>/dev/null \
    | xargs grep -ho 'tests="[0-9]*"' 2>/dev/null \
    | cut -d'"' -f2 | paste -sd+ - | bc 2>/dev/null || echo 0
}

find . -path '*/target/surefire-reports/*.xml' -delete 2>/dev/null  # avoid stale reports
OUT="$(run_tests)"; RC=$?
CURRENT="$(collect_failures)"
RAN="$(count_executed)"; RAN="${RAN:-0}"

if [ "$MODE" != "baseline" ] && [ "$RAN" -eq 0 ]; then
  echo "GATE INVALID: zero tests executed."
  [ -n "$SCOPE" ] && echo "  Scope filter '*${SCOPE}*' likely matched nothing — check gate_scope."
  echo "$OUT" | tail -20
  exit 2
fi

if [ "$MODE" = "baseline" ]; then
  printf '%s\n' "$CURRENT" > .harness/baseline.txt
  echo "Baseline captured: $(printf '%s' "$CURRENT" | grep -c . ) failing test(s)."
  printf '%s\n' "$CURRENT" | sed 's/^/  /'
  exit 0
fi

KNOWN="$(cat .harness/baseline.txt 2>/dev/null || true)"
NEW="$(comm -23 <(printf '%s\n' "$CURRENT" | sort -u) <(printf '%s\n' "$KNOWN" | sort -u))"
FIXED="$(comm -13 <(printf '%s\n' "$CURRENT" | sort -u) <(printf '%s\n' "$KNOWN" | sort -u))"

[ -n "$(printf '%s' "$FIXED" | grep -c .)" ] && [ -n "$FIXED" ] && {
  echo "Baseline failures now passing (re-baseline deliberately if intended):"
  printf '%s\n' "$FIXED" | sed 's/^/  + /'
}

if [ -n "$NEW" ]; then
  echo "NEW FAILURES — regression:"
  printf '%s\n' "$NEW" | sed 's/^/  ! /'
  echo "$OUT" | tail -40
  exit 1
fi

# A build failure with no test failures means compilation or plugin failure.
if [ "$RC" -ne 0 ]; then
  echo "Build failed with no new test failures — likely compilation:"
  echo "$OUT" | tail -40
  exit 1
fi

echo "Gate passed. ${RAN} test(s) executed, no new failures relative to baseline."
exit 0
```

Exit codes are three-valued on purpose: `0` passed, `1` regression, `2` gate invalid. The loop must treat `2` as a stop-and-report condition, not as a pass — an invalid gate is a broken instrument, not a clean bill of health.

## Gradle differences

Swap the runner and the report path:

```bash
GRADLE="./gradlew"; [ -x "$GRADLE" ] || GRADLE="gradle"
# fast:  "$GRADLE" :"${SCOPE}":test --console=plain
# full:  "$GRADLE" build --console=plain
# reports: */build/test-results/test/*.xml  (same JUnit XML schema)
```

Gradle's up-to-date checking will skip unchanged tests, which is usually desirable but can mask a stale pass — use `--rerun-tasks` in the full lane.

## Generation notes

- **Detect, do not assume.** Read the build files for the tool, module layout, and test task names. Prefer the wrapper.
- **Add a static-analysis lane only if the project already has one** — Checkstyle, SpotBugs, Spotless. Gate on new violations, same baseline logic. Do not introduce a linter the team has not adopted.
- **Formatters that fail the build** — Spring Java Format and Spotless both do this. Run the apply goal before the gate rather than failing on it.
- **Always show the generated script before the first run.** It executes build commands; the user should see them.
