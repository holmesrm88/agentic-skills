# Harness State Contract

The formats both phases read and write. Phase 1 creates these; Phase 2 advances them. Any agent picking up cold should be able to read `change-log.md` and know exactly where things stand.

## Layout

```
.harness/                      excluded via .git/info/exclude — never committed
├── change-log.md              current state + append-only history
├── init.sh                    the deterministic gate
├── baseline.json              pre-existing failures, captured once
└── features/
    ├── 01-<slug>.md
    ├── 02-<slug>.md
    └── ...
```

Zero-padded numeric prefixes so the execution order is the sort order.

## `change-log.md`

Two zones. The header is **rewritten** on every transition; the history is **append-only**. This split is what keeps the file useful — an agent reads the header to orient and only reads history when it needs to know why something was done.

```markdown
# Harness Change Log

<!-- CURRENT STATE — rewritten on every transition. Read this first. -->
## Current state

- **Story:** PROJ-1234 — Add tenant scoping to order lookup
- **Branch:** feature/PROJ-1234
- **Feature:** 03 of 07 — `add-tenant-column`
- **Phase:** red — failing test written, awaiting approval to implement
- **Last gate:** fast lane, 2 pre-existing failures (baseline), 1 new expected failure
- **Uncommitted:** `OrderRepositoryTest.java` (the failing test)
- **Blocked on:** nothing
- **Next:** implement `OrderRepository.findByTenant`, then re-run fast gate

<!-- HISTORY — append only, newest at the bottom. Never edit past entries. -->
## History

### 2026-08-24
- `init` — decomposed PROJ-1234 into 7 features. Baseline captured: 2 pre-existing
  failures in `LegacyImportTest` (unrelated, present on main).
- `01-add-tenant-entity` — red, green, committed `a1b2c3d`.
- `02-tenant-context-holder` — red, green, committed `d4e5f6a`.
- `03-add-tenant-column` — red. Test fails on assertion as expected.
```

Keep the header under about fifteen lines. If it needs more, the state is more complicated than the loop is designed for and something should be split.

## Feature files

YAML frontmatter for machine-readable state, markdown body for the human.

```markdown
---
id: "03"
slug: add-tenant-column
status: pending
source: PROJ-1234
depends_on: ["01", "02"]
tdd: true
gate_scope: orders
# Present only on features generated by the review panel:
# generated_by: review-panel
# round: 2
# source_finding: sec-01
# parent_feature: "03"
---

# Feature 03 — Add tenant column to order lookup

## Intent
One or two sentences. What behavior changes, from whose perspective.

## Acceptance criteria
- Specific, checkable statements.
- Each one should map to an assertion.

## Test to write first
The concrete failing test: which class, which method, what it asserts, and
what failure message proves the behavior is genuinely absent. Being specific
here is what makes the red step verifiable rather than a formality.

## Files likely touched
- `src/main/java/.../OrderRepository.java`
- `src/test/java/.../OrderRepositoryTest.java`

## Notes
Constraints, decisions made during decomposition, gaps flagged, conventions
this area follows. Anything a fresh agent would otherwise have to rediscover.
```

### Status values

| Status | Meaning | On-disk implication |
|---|---|---|
| `pending` | Not started | Working tree clean of this feature |
| `red` | Failing test written, not committed | Test file uncommitted |
| `green` | Implementation passes, not committed | Test + impl uncommitted |
| `committed` | Done | Working tree clean, commit exists |
| `blocked` | Cannot proceed | Varies — see change-log |
| `skipped` | Deliberately not doing this | Reason in the file |

`status` is authoritative. The change-log header is a summary and can lag; if they disagree, trust the feature file and correct the header.

### `tdd: false`

Set when writing a failing test first does not make sense, with the reason in Notes. Legitimate cases:

- **Pure refactor** with existing coverage — tests must pass identically before and after; a new failing test would be wrong.
- **Dependency or version bumps** — the gate is the test.
- **Configuration and build changes** — no behavior to assert at unit level.
- **Generated code** — test the generator, not the output.
- **Formatting or comments** — no behavior change at all.

Not legitimate: "this is hard to test." That usually means the design needs the pressure a test would apply.

## `baseline.json`

Captured once at init, before any feature work.

```json
{
  "captured_at": "2026-08-24T09:12:00Z",
  "commit": "a1b2c3d",
  "command": "./mvnw -q test",
  "failing_tests": [
    "com.solovis.legacy.LegacyImportTest#shouldParseFixedWidth",
    "com.solovis.legacy.LegacyImportTest#shouldHandleTrailingWhitespace"
  ],
  "notes": "Both pre-existing on main. Unrelated to PROJ-1234."
}
```

Every gate run compares against this. A failure in the baseline is not a regression; a failure outside it is, and the loop stops.

Re-capture the baseline only when rebasing onto a new main, and say so in the change-log — silently re-baselining can absorb a regression the loop introduced.

## Invariants

Worth checking whenever state is loaded:

1. At most one feature is `red` or `green` at a time. Two means an abandoned run.
2. A `pending` feature with uncommitted changes in its listed files is inconsistent — report rather than guess.
3. Every `committed` feature has a commit hash in history.
4. `depends_on` only ever points at lower-numbered features.
5. `.harness/` appears in `.git/info/exclude` and in no commit.
6. No feature has `round: 3` or higher, and no panel-generated feature has a panel-generated parent. Either means the review loop failed to converge — stop and escalate rather than continuing.
